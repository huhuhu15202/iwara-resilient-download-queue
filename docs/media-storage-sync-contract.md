# Iwara 与 Han1meViewer 仓库及传输协作契约

日期：2026-10-09。状态：联合实施中；核心仓库配置、双向传输接口和客户端适配已在两个工作区落地，已通过隔离模拟器双向 HTTP 往返测试。超过 5 GiB 的压力场景、真实设备 SAF 授权和正式环境验收仍未完成。本文同时描述已实现行为与尚待验收的目标，后者不得视为已交付。

## 共同目标与代码归属

电脑台账服务负责仓库目录、媒体身份、资料入账、双向传输任务和诊断；Han1meViewer 负责站内下载及手机到电脑归档；Iwara App 负责手机本地库、随机接收及播放；网页使用同一份电脑台账与媒体目录。

两个 Git 仓库保持现有位置。Iwara 对话负责 `G:\Iwara稳定下载队列\本地下载服务` 中的服务端及 Iwara Android 源码；“修复重复下载并添加批量下载”对话负责 `F:\新建文件夹\Han1meViewer-1.1.0`。客户端对话先核对接口依赖和变更范围，避免双方同时修改服务端。

电脑生产台账仍在既有 `dataRoot`。Han Room 历史、Iwara 手机库和电脑台账各自保存；升级使用兼容接口和增量迁移，保留已有任务 ID、视频 ID、观看记录和手机文件授权。

## 当前实现进度与限制

已实现并完成代码级验证的部分：

- 服务端新增版本化 `storageRepositories` 配置转换、路径验证/嵌套归属、原子保存与版本冲突检查，以及控制面板仓库表单。
- 服务端新增持久来源历史、逐文件库存、传输/批次/文件回执表；能力发现、库存检查、任务创建、状态查询、批次上传/确认/取消接口已接入。

- Iwara App Room 增至 v4，区分接收目录与多个扫描目录；多根目录扫描仅在完整成功后更新缺失状态。电脑随机下载 v2 已有持久任务 ID、逐视频 SHA-256、手机临时文件校验及台账事务登记。

## 已核实的当前实现

本机配置由 E、J、F 三个盘上的四个逻辑根目录组成：

| 目录 | 当前用途 | 新仓库配置对应角色 |
| --- | --- | --- |
| `J:\Video` | Iwara 主下载目录 | 下载目标、扫描、媒体提供 |
| `F:\Video` | Iwara 备用下载目录 | 下载目标、扫描、媒体提供 |
| `E:\hanime_download` | Han 历史目录 | 扫描、媒体提供 |
| `F:\video\hanime_download` | Han 新归档接收及扫描目录 | 接收上传、扫描、媒体提供 |

当前 Iwara 下载保留空间阈值为 5 GiB。Han 接收器直接使用 `han1meDownloadRoot`；历史编号接口合并扫描 `han1meHistoryRoots` 与接收根目录，返回实际媒体文件对应的数字编号。任一启用的配置根目录不可用时编号接口失败，避免提交不完整清单。

这里的既有“历史编号接口”实际提供当前文件编号，并非服务器持久下载历史。兼容期间不改变其含义，不能把仅有历史但已经没有文件的编号混入返回结果：旧客户端会用它决定跳过上传和清理手机。新增独立的持久历史查询，跨仓库停用、迁移及文件移除保留曾下载事实；新客户端分别消费历史和库存，旧客户端继续使用当前文件清单。旧客户端清空 Room 后仍可能失去电脑已移除文件的去重历史，这属于旧协议限制，不以改变旧接口含义来掩盖。

已有接口与格式需兼容：

| 用途 | 当前接口/格式 | 客户端 |
| --- | --- | --- |
| 电脑 Han 编号集合 | `GET /api/mobile/han1me-download-codes` | Han1meViewer 的 Room 去重历史 |
| Han 文件上传 | `POST /api/mobile/han1me-archive` 保留 v1；新客户端通过 `POST /api/mobile/transfers` 冻结清单，再 `PUT /api/mobile/transfers/{id}/batches/{batchId}/archive` 使用 v2 | Han1meViewer；v2 按每个媒体/封面/资料文件确认 |
| 电脑 Han 播放量回填 | `/api/mobile/han1me-view-counts` 及 `/missing` | Han1meViewer |
| 电脑 Han 作者等元数据回填 | `/api/mobile/han1me-video-metadata` 及 `/missing` | Han1meViewer |
| 手机资料快照 | `GET /api/mobile/catalog.sqlite` | Iwara App |
| 随机分批接收 | `POST /api/mobile/random-download` 保留 v1；v2 返回持久 `transferId`，通过 `/api/mobile/transfers/{id}/batches/{batchId}/archive` 下载和确认 | Iwara App |
| 网页多选下载 | 已有批量 ZIP 与状态接口 | 浏览器 |

Han 上传器约 1 GiB 视频数据一批；Iwara 随机接收当前每包媒体上限为 4,500,000,000 字节。两种 ZIP 的内容格式和读取方式不同，首次升级保留各自编码器，统一配置、身份和任务状态。

## 统一仓库配置

统一配置使用版本化的 `storageRepositories` 列表。每条目录有稳定 `id`、显示名、绝对路径、来源、启用开关、角色、优先级和剩余空间阈值。目录数量可增加；“三个位置”不再成为代码中的固定数量。

角色定义：

- `scan`：发现媒体和同目录资料，并送入对应来源的入账器。
- `serve`：允许电脑播放、网页下载和发送到手机。
- `receive`：允许接收手机上传；一个来源可设置首选和备用接收仓库。
- `download`：站点下载完成后的落盘目标；优先级和容量决定选哪一个。

`source` 使用 `iwara`、`han1`、`other`；既有 Han 平台别名统一映射为 `han1`。Windows 路径保存在电脑端，App 选仓库 ID，手机接收目录继续由 Android SAF 授权管理。

同路径按 Windows 大小写不敏感规则判重。父子目录可以同时配置，但文件由最长匹配路径所属的仓库处理；例如 F 的 Han 子目录由 Han 入账器处理，父目录的 Iwara 扫描跳过该子目录，避免重复入账或错分来源。

控制面板增加仓库管理：添加、停用、测试目录、预览扫描数量、设置角色/优先级/保留空间和保存。检测目录的存在、读写权限、磁盘容量及嵌套关系后再提交。停用仓库不参与清单；启用但失联的仓库必须显示异常。修改路径不移动文件，也不删除旧台账。

第一次升级从现有 `downloadRoot`、`fallbackDownloadRoot`、`externalMediaRoots`、`han1meDownloadRoot`、`han1meHistoryRoots` 生成兼容配置。新配置成为统一来源；保存时原子写入实际正在使用的配置文件，并保留上一份可恢复配置。环境变量覆盖要在管理页标明，避免保存后被启动脚本悄悄覆盖。

已开始的任务固定使用启动时的仓库和配置版本；新设置只影响新任务。切换扫描根时等待旧扫描收尾再启用新配置，不切断当前传输。若某项暂需重启，页面明确显示待生效状态并等待服务空闲处理。

## 媒体身份与确认语义

将以下三种信息分开保存和展示：

1. 下载历史：该来源编号曾下载过，用于避免再次下载。
2. 文件库存：某个仓库或手机 URI 当前有哪些真实文件，以及各文件的大小、SHA-256 和可选画质。
3. 台账入库：文件与元数据已提交 SQLite，播放/资料同步可以查询到。

统一媒体键由来源和来源 ID 组成。既有 `taskId`、`videoId` 不改；无来源 ID 的媒体继续保留原任务，完整指纹提供内容身份。一个来源编号可对应多个画质或不同内容文件；编号相同不证明文件相同，采样指纹只用于筛选，完整 SHA-256 才用于内容一致性判断。

初始核对时，Han v1 流程只用电脑编号集合筛选待传文件，并按确认编号清理手机目录；它无法证明电脑保存了手机的每个画质/文件。当前新版客户端优先协商 v2：逐文件匹配来源、编号、角色、相对路径、长度和完整 SHA-256，确认服务端持久保存且写入库存后，才将本次冻结的原 URI 纳入可选清理范围。旧服务仍走 v1，但 v1 编号回执不授权自动清理。

初始核对发现的四个 Han 边界及当前覆盖情况：

- v2 在读取前核对文件 URI 与可用长度信息，并在构建归档时重新校验长度/哈希；历史占位长度按未知处理。客户端旧 v1 路径仍不具备完整内容确认，因此保持手机副本。
- 客户端计数并显示源端不可读 PNG；电脑必须通过 v2 媒体与资料文件确认。缺封面的电脑补图结果尚未通过实机验收，不能将其宣传为已验证功能。
- “仅今天下载”过滤候选记录；可清理集合限制在本次上传并取得 v2 入账回执的原始 Room 行。
- 删除调用针对已冻结 URI，并检查 SAF 授权及删除结果；授权失效或无法可靠确认时保留 Room 历史/文件状态，不用当前目录缺少某编号推断原 URI 已不存在。

允许清理的条件是：本次清理范围匹配、每个源文件身份匹配、电脑文件保存与台账提交确认、原 URI 授权有效。手机删除成功或可证明原 URI 已不存在后，才能更新对应 Room 文件记录；历史去重记录继续保留。整目录删除只能用于目录内所有内容都在确认范围内的情况，不能顺带删除未上传画质或其他文件。

区分复制完整性与下载源完整性：归档时计算的指纹可证明电脑保存了同一份手机内容，不能证明文件从最初下载结束后未损坏。新下载完成时保存完整 SHA-256 及长度，归档时对照；有基准且一致才能标记下载源校验通过。旧记录没有基准时只标记复制校验通过，不补造可信哈希。旧数据自动清理的策略需显式确认，默认保留手机副本；用户可在逐文件复制校验和入账成功后明确选择清理。

客户端收到回执后先持久保存批次、逐文件确认和清理状态，再执行逐文件删除及 Room 更新。应用中断后从保存状态续跑；删除完成但 Room 尚未更新时复核同一原 URI，不重新上传、不改用当前目录、不重复扩大清理范围。

v1 服务上传成功表示 ZIP 校验及文件写入完成，随后触发入账扫描；它不提供逐文件入账证明。v2 持久任务区分已保存和已入账状态，服务通过后续任务查询重新核验文件库存并提交逐文件回执。过滤、冲突或入账失败保留错误并阻止客户端清理。

Iwara 手机接收器的 v2 路径核对 ZIP 长度、CRC、文件大小及发送清单中的完整 SHA-256，再事务性登记媒体身份和元数据；v1 兼容格式仍没有可比较的预期完整指纹。

## 传输任务与兼容升级

建立持久传输任务，包含任务 ID、方向、来源、仓库 ID、配置版本、批次、文件身份、状态和错误原因。统一状态语义为：准备、传输、内容校验、文件发布、台账入库、接收端确认；失败和取消独立保留。

服务重启后可查询此前任务和回执；重试沿用同一批次和文件身份，不能重新随机选一批当作重试。两端在确认前核对源文件大小/修改时间，内容变化时停止并重新建立清单。

共同清单至少包括来源、来源 ID、原 taskId/videoId、标题/作者/日期/标签/播放量、文件相对路径、大小和完整 SHA-256；不得包含令牌、电脑绝对路径或个人网络地址。保留两种 v1 格式，通过服务端适配共享模型，客户端协商新版本后再使用新格式。

目录配置第一阶段即可让现有已安装 App 继续调用旧接口，无需因更换电脑路径重新打包。文件级确认和更完善的恢复需要一次客户端升级；升级保留 Room、手机台账和目录授权。

新客户端遇到不支持能力发现或新版回执的旧服务时，可继续 v1 编号查询和显式上传，但不得降级为按编号自动清理。旧客户端调用新服务时维持原 v1 字段和格式；服务端兼容升级不能修复旧客户端自身的编号清理风险。需要清理手机副本的使用流程应先完成 Han 客户端升级，不能宣称仅升级电脑服务就已安全。

能力发现接口现提供支持协议版本、可选择仓库、批量目标大小和硬限制。默认目标批量约 1 GiB；视频不拆开，超过目标的单文件独立成批，但不能超过客户端支持上限。接收前还需继续验证暂存 ZIP、解压文件与保留空间的容量预检，以及同盘多任务共享容量预留。

网页显示的“传输完成”表示 HTTP 发送完成；只有能报告文件校验/本地入库的 App 才能显示“已保存并入库”。各入口共享任务状态和诊断，但保留各端实际能证明的完成程度。

## 分阶段实施与验证

1. 服务端仓库注册表、旧配置兼容、路径所属规则及管理界面。验证四个逻辑根目录、父子目录隔离、停用/失联及 5 GiB 规则。
2. 文件库存接口、持久回执和清理确认。Han 客户端接入文件级核对，确认失败保留手机文件。编号去重表继续使用。
3. Iwara 随机发送清单加入内容指纹，手机接收器核对预期指纹；随后两端接入统一传输状态、批次重试和能力发现。
4. 全链测试及两个客户端实机确认。只有客户端迁移完成后再讨论停用旧接口。

隔离验证使用临时 E/J/F 仓库替身与独立端口，覆盖：同编号不同画质、空编号目录、同内容改名、多位置副本、后补 JSON、过滤项、目录失联、容量不足、部分传输、中途取消、回执丢失、入账失败、服务重启、重复提交及连续多批任务。每个方向至少完成两轮、累计 12 次真实 HTTP 传输，确认临时文件回收、完整指纹和台账一致；真实手机验证 SAF 保存/清理和旧记录保留。

客户端清理专项验收还需覆盖：仅今天模式不清理昨天的记录；同编号另一画质已在电脑时仍补传缺失文件；源文件截断或读取中变化不产生可清理回执；可读封面、源端缺封面和授权失效分别报告；换过手机存储目录后核对原 URI；目录内存在未完成下载或额外文件时禁止整目录清理；电脑完成落盘但 SQLite 入账失败时不清理手机文件。

兼容及恢复验收：旧 v1 字段含义不变；新客户端连旧服务时不自动清理；停用或迁移仓库后持久历史仍可查询且不混入旧库存清单；有下载基准哈希时检测同长度损坏，无基准旧文件明确显示验证等级；回执保存、删除与 Room 更新的各个边界强制中断，恢复后不误删、不丢历史、不重复归档。

实际媒体的移动、删除、批量重下和生产服务重启按单独操作处理；联合设计和隔离验证不执行这些操作。

## 双方文件分工及核验依据
